Two security issues were identified and corrected, both **low** severity, and
both recorded as **declined** rather than filed: one is hardening, the other
fails closed. No advisory was drafted and none was published. This audit did
not change the project version.

This is a follow-up to [audit-2026-09-16](audit-2026-09-16.md), which found
eleven issues across the whole checkout. The repository has advanced by 173
commits and roughly 22,800 inserted lines since then, so the manual review
concentrated on what that work added — the report upload and comparison, the
HTML/PDF/SARIF reports, the operator area's self-update, threshold profiles,
the upgrade rehearsal and remediation verification — while the automated

The small number of findings is a result about the new code, not a shortened
review: the surfaces examined below were, with the two exceptions named,
already defended, usually with the reasoning written down beside them.

## Scope and method

A source and configuration audit with local regression testing. Not a
penetration test of a deployed service, and not a proof of security.

Reviewed trust boundaries:

- The uploaded-report parser (`webapp/imports.py`) — the only structure the
  service parses that it did not write.
- Report rendering: HTML escaping and URL schemes, CSV formula neutralisation,
  PDF text-object escaping, the SVG badge.
- The operator area: proxy authentication, the allow-list of operators, the
  cross-origin check on every POST, documentation slugs, and the self-update
  path — download bounds, Sigstore attestation, tar member validation,
  downgrade refusal and the worker's Redis-driven follow.
- SSRF address classification, including IPv4-mapped, 6to4, Teredo, NAT64 and
  deprecated IPv6 site-local.
- MCP bearer-token verification: algorithms, issuer, audience, expiry, key
  selection and JWKS fetch bounds.
- Submission field allow-listing, forwarded-client-address handling, rate and
  probe limits, uuid capabilities, purge authorisation and receipt signing,
  result encryption and export signing.
- Response security headers across pages, errors, JSON, exports, the badge,
  static files, redirects and the operator area.
- First-party JavaScript for DOM injection sinks; the translation catalogues'
  markup interpolation.
- Generated reverse-proxy configuration, Compose files and GitHub Actions.

## The findings

**The web application sent no `Strict-Transport-Security` header.** The
generated nginx site states that it adds no security headers because "the
application sends its own, and an `add_header` here would be one more place
they can disagree" — and HSTS was the one the application did not send, so a
TLS deployment built by `docker/setup-wizard.py` had none at all. A service
whose own subject is HTTPS enforcement, and whose hardening catalogue grades
`hstsLongMaxAge` and `hstsIncludeSubdomains` on the instances it scans, was
asking less of itself than of them.

The header is now sent over TLS only, as RFC 6797 section 7.2 requires: a
browser may not record HSTS from a cleartext hop. Because the container runs
uvicorn deliberately *without* `--proxy-headers`, the request scheme is the
scheme of the hop from the proxy, so `X-Forwarded-Proto` is the only thing
that knows — and it is believed exactly where `COS_WEB_TRUST_FORWARDED_FOR`
already says a proxy writes such headers, which is the trust decision
`client_address` makes. The value is `max-age=63072000; includeSubDomains`.
`preload` is deliberately **not** sent: it is an effectively irreversible
submission to a list browsers ship, and it belongs to whoever owns the domain
rather than to the software running on it.

**`webapp.purge.verify` raised instead of returning `False`.** It compared the
expected digest with the receipt's signature as `str`, and
`hmac.compare_digest` raises `TypeError` on a string outside ASCII — so a
receipt edited to carry one answered an auditor with a traceback rather than
the `False` the function is read for. Both sides are encoded now, exactly as
the purge endpoint has always compared its bearer token. The endpoint was
never affected, and no forged receipt ever verified: the defect failed closed.

## Validation

- The complete suite passed before the changes — **3,199 tests, 32 skipped**,
  420 seconds — and again afterwards, with four new HSTS tests and one new
  receipt test. Each new test was confirmed to **fail without its fix**; the
  receipt test fails with the exact `TypeError` the fix removes.
- Bandit found no medium-or-higher severity/confidence issues across the
  scanner, plugin, web application, scripts and Docker Python code (59,406
  lines, 75 documented `# nosec` suppressions). It did not find either issue
  above, which is the usual limit of it.
- Offline Zizmor reported no findings over all 23 workflows and the composite
  action, with the repository's existing suppressions (4 ignored, 46
  suppressed). This is not a claim that each suppression was re-proven.
- **119** locked Python distributions across all extras and dependency groups
  were checked against OSV: no known vulnerabilities. `pip-audit` itself could
  not run locally — its isolated `ensurepip` aborts under this sandbox — so
  OSV, which is pip-audit's own default source, was queried directly for the
  same pinned set. This does not cover every version the lower-bound
  specifications permit.
- A **full Git-history secret scan** was run, which the previous audit listed
  as a remaining limit: 4,913 blobs across all 532 commits and every ref were
  searched for AWS keys, GitHub tokens, Slack tokens, private-key headers and
  OpenAI-style keys. Nothing was found. No tracked file matches a
  credential-file name.
- SSRF address classification was exercised directly against the
  implementation for NAT64 (`64:ff9b::127.0.0.1`), 6to4, Teredo,
  IPv4-mapped loopback, link-local metadata addresses and site-local; all are
  refused, and ordinary public addresses are not.
- The advisory-coverage check passes with the two new records (38 records,
  every Security entry from 1.14.0 forward accounted for). The generated
  frontend documentation check passes after regeneration.

## Limits and remaining operational risks

- No deployment was started for this audit: no Docker build, no Compose
  stack, no real Redis, no Authentik sign-in, no browser-engine run. The
  previous audit covered those and nothing in the two changes here alters a
  container boundary; the HSTS change should still be confirmed against a
  real proxy before it is relied on, because it depends on that proxy setting
  `X-Forwarded-Proto` and on `COS_WEB_TRUST_FORWARDED_FOR` being on.
- **A deployment that terminates TLS at a proxy and leaves
  `COS_WEB_TRUST_FORWARDED_FOR` off still sends no HSTS.** That is the safe
  direction — it is better than a direct-TLS service being taken for a
  proxied one — but it means the fix is not automatic for every operator. The
  Docker README and the setting's own documentation now say so.
- `includeSubDomains` is a statement about the whole domain the service is
  served from. An operator hosting this on a domain whose other subdomains
  are not HTTPS-only should override it at their proxy. This was judged the
  right default because it is what the project asks of the instances it
  scans, but it is a deployment-visible choice worth the maintainer's
  attention.
- The review of the 22,800 new lines was concentrated on the security-relevant
  surfaces named above. Test files, translation catalogues and generated
  documentation were not read line by line.
- No live external target was scanned, no load test was run, and no fresh
  CodeQL database was built. The vendored JavaScript bundles were treated as
  application inputs, not independently audited.
- Everything the previous audit listed under its own limits — the operator's
  explicit private-target allowance, a compromised Redis or identity proxy,
  the reference-data trust model, and per-scan process and memory use — still
  stands unchanged.

## Maintainer actions

Decide whether `includeSubDomains` is right for the domains this service is
deployed on, and whether `preload` should ever be offered as an operator
setting. The two new records are `declined` and need no publication decision;
the eleven drafts from the September 16 audit are still awaiting one.
