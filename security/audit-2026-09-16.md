# Repository security audit — 15–16 September 2026

## Outcome

Eleven security issues were identified and corrected: three high, seven
medium and one low severity. Each has a local **draft** advisory with
tag-level evidence, affected versions, mitigations and distribution scope.
No advisory was created or published on GitHub; no CVE was requested.

The review began against the whole checkout at `1d62e54`, not just its
translation diff. While the work was in progress, the repository advanced:
the security implementation was committed in `4204e54`, and the maintainer
set the version to 1.23.2. Follow-up validation used `3bf7f71` plus the
remaining audit documentation and test corrections. The latest available
release tag checked was **v1.23.1**; the fixes are in the source for
**1.23.2**. This audit did not change the project version or create a release.

## Scope and method

This was a source and configuration audit with local regression testing,
not a penetration test of a deployed service or a formal proof of security.

Reviewed trust boundaries included:

- Scanner HTTP sessions, redirects, body limits, DNS/TLS address pinning,
  safe probe methods, demo credentials and same-origin companion probes.
- Plugin webhook destinations, signing and redirects; optional monitoring
  listeners; configuration, baseline files and self-update command execution.
- Web submission validation, SSRF exclusions and approval policy, forwarded
  client addresses, rate limits, queue execution and job cancellation.
- UUID capabilities, Redis transitions and TTLs, erasure, encryption,
  response caching, result exports and export signing.
- Admin proxy authentication and browser-origin checks; MCP token
  verification, key fetching and in-process API workflows.
- Frontend escaping, translated markup interpolation, DOM insertion sinks,
  CSP and locally vendored documentation assets.
- Docker and authentik deployment configuration, generated secret-file
  permissions, package/build scripts, reference-data verification and
  GitHub Actions privilege/input handling.

Manual review was complemented by Bandit, an offline zizmor workflow scan,
a locked Python dependency audit, high-signal credential-pattern searches
(returning filenames rather than secret values), type checking and the
repository test suite. Security regressions use synthetic fixtures and
local HTTP servers, never a real OpenCloud deployment.

## Important findings

Requests' ambient configuration was not an explicit scanner feature:
matching or default netrc credentials could be sent by supposedly anonymous
probes, and environment proxies could bypass the connection-pinning pool.
The [Requests authentication documentation](https://requests.readthedocs.io/en/latest/user/authentication/)
documents netrc use and its `trust_env` opt-out. Both owner and parallel
probe sessions now opt out. Explicit plugin proxy and CA configuration
remain supported.

Two DNS checks did not pin webhook delivery. The HTTP request resolved the
receiver again, leaving a third-answer rebinding window. The new adapter
binds the actual connection to validated addresses, while retaining the
hostname for Host, SNI and certificate verification. This is a follow-up
to the older `webhook-validation-toctou` advisory, not a rewrite of its
historical record.

A Requests redirect could also consume an unbounded body before the
scanner's cap ran, including with `allow_redirects=False`: Requests prepares
the next request internally. Redirect handling is now fully manual and
capped. Tests cover both guarded and unguarded scans and unfollowed redirects.

A running thread is not stopped when its awaiter times out. The old
`wait_for(to_thread(...))` released a worker slot while probes could keep
running. The fix uses a spawned process, killed and reaped on timeout or
cancellation. [ADR 0053](../adr/0053-a-scan-timeout-ends-its-process.md)
records the deployment trade-off. Python distinguishes task cancellation
from blocking work delegated to threads in its
[asyncio documentation](https://docs.python.org/3/library/asyncio-task.html).

Erasure and expiry must remain final even if a worker is already running.
The new conditional transition checks metadata and status existence in the
same Redis operation that writes completion. Tests include erasure between
the metadata read and the attempted write.

## Validation

- Targeted scanner/webhook, worker, MCP authentication, origin and erasure
  suites passed during implementation.
- The final complete suite passed **2,213 tests**, with **17 skipped**, in
  273.72 seconds. Earlier runs caught a missing test-index entry, advisory
  comment headers and a test-fixture backlog smaller than the supported
  probe concurrency. Those were corrected before this final passing run.
- Focused regression tests cover credential isolation, pinned webhook
  delivery, redirect caps, origin normalization, erasure races, JWKS outage
  and concurrent-fetch bounds, process cleanup, body limits, loopback browser
  requests and pre-write secret-file permissions.
- Type checking passed for **72 source files**.
- Bandit found no medium-or-higher severity/confidence issues in the
  scanner, plugin, web app, scripts or Docker Python code, both before and
  after the fixes. This did not find the logic bugs above.
- Offline zizmor reported no findings with the repository's existing
  suppressions (4 ignored, 49 suppressed); this is not a claim that each
  suppression was independently re-proven.
- pip-audit found no known vulnerabilities in the 96 exported locked Python
  distributions, including all extras and development groups, on
  15 September 2026. This does not cover every version permitted by the
  lower-bound dependency specifications.
- Advisory schema and Security-changelog coverage validation passed.
- Generated frontend documentation/search-index checks and diff whitespace
  checks passed. The prior translation work was preserved.

## Limits and remaining operational risks

- Docker was installed but its daemon was unavailable. Container images,
  real Redis Lua execution, and a deployed authentik/proxy stack were not
  exercised. Redis state transitions were tested using the in-memory backend;
  the real backend's atomic Lua operation was reviewed.
- The vendored JavaScript bundles were inspected as application inputs and
  their upstream advisory pages consulted, but their entire transitive
  dependency trees were not reconstructed or independently audited.
- No live external target was scanned. There was no browser-engine exploit
  run, large-scale load test, full Git-history secret scan, OS-package scan,
  or fresh CodeQL database analysis.
- The new body-size/deadline and scan-process bounds do not replace reverse
  proxy connection limits, container memory/PID limits or egress filtering.
  A native resolver can still delay request-side DNS validation.
- An operator's explicit private-target/private-webhook allowance remains a
  deliberate bypass of public-address restrictions. A compromised Redis,
  identity proxy or trusted host is outside the guarantees of these fixes.
- Reference-data verification keeps its documented optional/fallback model;
  this audit did not redefine that accepted trust policy.
- Before deployment, exercise the new process lifecycle and Redis transition
  against the production-equivalent container stack. Monitor process and
  memory use: each active web scan now owns a Python process.

## Maintainer actions

Review the eleven draft advisories and their severity/ranges before deciding
whether to publish them. Consider credential rotation for accounts whose
netrc entries may have reached untrusted targets, and for wizard outputs
previously writable/readable by other local accounts. Keep the existing
release and advisory-publication decisions manual.
